## Goal

An AI assistant connected to OpenRace can answer the roadmap's questions in one or two tool calls, and it can tell the user how fresh and how sure each answer is:

| Question | Tool call(s) |
|---|---|
| I'm in Nha Trang 1–15/12: which races are nearby on those days? | `search_races { near: "nha-trang", from, to }` |
| I just finished VMM: next trail run, cheapest first, close to HCMC | `search_races { after: "<race or series>", type: "trail_run", sort: "price", fromPlace: "hcmc" }` |
| All races under 300k at today's tier | `search_races { maxPrice: 300000 }` |
| How many times has Lâm Đồng Trail been held? | `find_series { name }`, then `get_series { id }` |
| Sort upcoming races by price, longest or shortest distance | `search_races { sort }` |
| When was this race last checked? Can I trust it? | `get_race { idOrSlug }` (freshness, confidence, flags, sources) |

A second goal: **shake out the API contract before the frontend freezes it.** Everything awkward the model runs into (unclear names, missing filters, confusing nulls) goes on a list for openrace-api.

## Roadmap fit

- **Serves** path step 5 ("Open it up: a public API and an MCP server"). Also exercises step 2 (the questions) end to end.
- **Trust principles:** every tool result carries each race's `freshness.status`, `confidence` and `flags`, and the list's `meta.excluded` counts, so the assistant can say "3 races left out because they have no price yet". Unknown values stay `null` and are described as unknown, never as free or zero (principle 3). Sources are returned as links (principle 1).
- **Constraints:** runs on the Cloudflare plan the user upgraded to on 2026-09-24 (Workers Paid, $5/month, within the roadmap budget). No paid APIs. No Claude API calls inside the server.
- **Non-goals respected:** read-only; nothing about people; no ticket selling.
- **Out of scope:** the frontend (next, after this), API keys (decided from the metrics this plan produces), stats tools (path step 4).

## Decisions

**Where and how**
- New repo `openracevn/openrace-mcp`, a Cloudflare Worker. openrace-api's `architecture.md` already says the MCP server lives in its own repo.
- A **remote MCP server over Streamable HTTP** at `POST /mcp`, **stateless** (no sessions, no Durable Objects): every tool is a pure read. `GET /mcp` answers 405 so SSE clients stop retrying.
- **Library (decided 2026-09-24):** the MCP TypeScript SDK's `WebStandardStreamableHTTPServerTransport` with `sessionIdGenerator: undefined`, a new `McpServer` + transport per request. Not `agents`/`McpAgent`: openwalletvn/mcp used it and blew the Durable Object SQLite quota on client reconnect loops (its `.claude/debug-notes.md`, 2026-06-06), then moved to this pattern. Use `openwalletvn/mcp/src/index.ts` as the reference for the handler, the `registerTool` wrapper (one place for metrics) and tool files (zod schema, `readOnlyHint`, errors as `isError`).
- It calls openrace-api through a **service binding** (`[[services]] binding = "API", service = "openrace-api"`), not the public URL: no extra hop, no CORS, no public rate limit.
- **Domain:** `openrace-mcp.<account>.workers.dev` for now; a custom domain later.
- **No auth, no Langfuse.** Public and rate-limited per IP (60/min, `[[ratelimits]]` in the MCP Worker, hashed with the same `IP_HASH_SALT` as the API so `index1` caller keys match). Analytics Engine + Workers logs are the only telemetry.
- Local dev: `pnpm dev` runs `wrangler dev` plus the MCP Inspector; the service binding reaches a locally running openrace-api through the dev registry, or the deployed one with `remote = true` on the binding. Never point a local client at the deployed MCP URL.

**openrace-api changes (small, in that repo)**
- The rate limiter already skips requests with no `CF-Connecting-IP` (`if (!key) return next()`), which is what a fresh `Request` over the binding looks like. Make it explicit: the MCP Worker sends `X-MCP-Secret: <MCP_SECRET>`; when it matches, the API skips the limit and tags its metric row `source = mcp-upstream` (not `mcp`, so one tool call isn't counted twice).
- Metrics: the MCP server writes one row per `tools/call` in the `openrace_api_requests` dataset with the `metrics.md` layout: `blob1 = mcp`, `blob2 = <tool name>`, `blob3 = ok | error`, `blob7 = tools/call`. **`blob4` is the user-agent family, not `clientInfo.name`**: a stateless server only sees `clientInfo` in `initialize`, never in `tools/call`. Update `metrics.md` for `blob4` and the new `mcp-upstream` source.
- **What people ask (`blob8`, decided 2026-09-24):** the assistant never sends the user's words, only tool arguments, so the arguments are how we learn what people look for. Both the MCP tool call and the REST `/races` request write a coarsened summary to `blob8` (one shared helper so both match), keys sorted, `;`-separated, e.g. `near=nha-trang;type=trail_run;sort=price;when=2026-12;maxPrice=300k`.
  - Kept as is: place ids (`near`, `fromPlace`, `province`), `type`, `distance`, `sort`, `fresh`, `series`, `organizer`, `after`, `when` keywords, and race id/slug on `get_race`. These are about races, not people.
  - Coarsened: `from`/`to`/`at` to the month (`2026-12`); `maxPrice` rounded up to the next 100k; `page` dropped.
  - Never stored: the words of `query` (free text could hold a person's name). Store `query=1` only. Unknown keys are dropped, and the blob is capped at 256 characters.
  - Roadmap fit: principle "focus on data, not people" holds because only race filters are kept. Use it to rank the roadmap's question table and to feed the contract list (step 6).

**Tools** (names and arguments in plain English, because the model reads them)

| Tool | Wraps | Notes |
|---|---|---|
| `search_races` | `GET /races` and `/races/search` | Arguments: `query` (name words), `when`, `from`, `to`, `near`, `province`, `type`, `distance`, `maxPrice`, `at`, `sort`, `fromPlace`, `after`, `fresh`, `series`, `organizer`, `page`. With `query` it uses `/races/search`. |
| `get_race` | `GET /races/{id}` or `/races/by-slug/{slug}` | Everything, including each course's price today, freshness, geo label, flags and source links. |
| `list_places` | `GET /places` | The 13 place ids `near` and `fromPlace` accept. |
| `find_series` | `GET /series` | Filters by folded name on the MCP side (the list is small). |
| `get_series` | `GET /series/{id}` + `GET /races?series=&when=all` | Editions (`label`: "5th edition (4 on record)") and each edition's date. |

- **Compact results:** a list returns one short line or small object per race (name, dates, place label, courses with meters and today's price and status, freshness status, id/slug), plus `meta` (the `at` date and the `excluded` counts) and paging. `get_race` gives the details. Keep results small; models pay for every token.
- **Tool descriptions teach the rules:** prices are VND; "today" is Vietnam's date; `at` changes the price date; a race with no price is unknown, not free; `stale` means the data may be out of date; place ids come from `list_places`; old names like "Nha Trang" work through `near`.
- **Errors** come back as tool errors with the API's message (e.g. `No race or series "vietnam-mountain-marathon"`), so the model can retry with `search_races { query }`.

## Steps

1. **openrace-api:** the binding exemption (`X-MCP-Secret`) in the rate limiter, `source = mcp-upstream` for binding calls, the shared argument-summary helper writing `blob8` on `/races` requests, and `metrics.md` updated (`blob4`, `blob8`, `mcp-upstream`). Tests (including: `query` text never appears in `blob8`). Deploy.
2. **openrace-mcp repo:** scaffold (Worker, TypeScript, wrangler with the service binding to `openrace-api`, the Analytics Engine binding, the rate limiter), `README.md`, `AGENTS.md` pointing at openrace-data's roadmap like openrace-api's does.
3. **Tools:** implement the five tools against the API's current response shape. Unit tests with a mocked API binding (fixtures from real responses).
4. **Eval:** a script (`npm run eval`) that connects with the MCP SDK client to a local `wrangler dev` (or the deployed URL) and runs the six questions as tool calls, checking that each returns sensible data and that `meta.excluded` and freshness come through. Keep its output in the day summary.
5. **Try it with a real assistant:** connect it to Claude (Claude Code `claude mcp add --transport http openrace <url>/mcp`, or Claude Desktop) and ask the six questions in plain Vietnamese and English. Write down every awkward moment.
6. **Contract list:** turn step 5's notes into a short list of openrace-api changes (renames, missing filters, confusing fields). Already known: the race detail flattens `location` into `venue`/`city` while the data files nest it; `priceAt` is the name for both the race's and each course's price. Decide each item with the user before the frontend plan.
7. **Deploy** the MCP Worker; add its URL to openrace-api's README and open items; update `status.md` and the roadmap (path step 5: MCP done).

## Check at the end

- The six questions answered through the deployed MCP server, by the eval script and by a real assistant, with the requests and answers pasted into the day summary.
- Metrics show `source = mcp` rows with tool names and a `blob8` summary; one Analytics Engine query lists the most common searches (MCP and REST together), with no `query` text in any row.
- The contract list exists and has been reviewed with the user.
